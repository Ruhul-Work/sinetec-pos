## 4. Known application work before full use

- Dashboard legacy business queries are removed; cards/charts now use a safe zero state until each new module supplies its approved metrics.
- Phase 0.5 application cleanup is complete: route-detached legacy product, purchase, POS, stock, report, promotion and old transaction controllers/models/services/views were removed after the new Git baseline tag was created.
- The retained Supplier controller is now master-data only; its old purchase/return/ledger coupling was removed and its browser-parsed CSV/XLSX import was aligned with the clean supplier schema.
- The shared helper file now contains only retained image upload/path and branch/warehouse/fiscal-year context helpers; legacy storefront product, cart, coupon and shipping helpers were removed.
- Purchase Order, Purchase Receipt and Purchase Return each have independently permission-mapped routes.
- The first Phase 1 module is complete: Units and company-wide universal Unit Conversions have CRUD screens, reverse conversion display, duplicate-pair protection, reference-safe unit deletion and automated feature coverage.
- The three Phase 1 category masters are complete: Raw Material, Part and Finished Product categories have separate CRUD routes/tables/permissions, optional parent hierarchy, cycle protection, Select2 parent lookup and reference-safe deletion.
- Raw Material Master is implemented with material/packaging/consumable classification, category/base-unit/optional-brand lookup, image handling, list filters, independent RBAC and downstream-reference delete protection. Stock quantity, rates, alternate units and suppliers are intentionally not stored in this master.
- Part Master is implemented with `MAKE`/`BUY`/`BOTH` procurement modes, category/base-unit/optional-brand lookup, image handling, list filters, independent RBAC and downstream-reference delete protection. Made and purchased quantities will later enter the same part stock ledger.
- Finished Product Master is implemented with category/base-unit/optional-brand lookup, optional default retail/wholesale prices, image handling, filters, independent RBAC and downstream-reference delete protection. The defaults do not replace immutable sale-line and approved monthly-report price snapshots.
- Domain Unit Mapping is implemented through one compact tabbed screen backed by separate `raw_material_units`, `part_units` and `finished_product_units` tables. Base units remain implicit at factor 1; duplicate/base-unit mappings and process-incompatible usage are blocked.
- Raw Material Supplier and Part Supplier Mapping are implemented as separate route/controller/RBAC modules backed by `raw_material_suppliers` and `part_suppliers`. Each mapping stores the supplier's item code, lead days and one preferred source per item; purchase prices remain transaction-derived.
- Warehouse-wise Raw Material, Part and Finished Product Reorder Levels are implemented as separate route/controller/RBAC modules. Minimum quantity is required; fixed replenishment and maximum/target quantities are optional. A blank fixed quantity is stored as zero and means future demand-based planning rather than an automatic purchase or production action.
- Laravel 13 cache/session hardening is active: sessions use JSON serialization, cached PHP classes are disabled, permission and branch-switch caches store plain arrays/scalars, and the browser smoke-test regression in the shared topbar is resolved.
- The Phase 2 Stock Posting foundation is implemented for Raw Material, Part and Finished Product. Each domain has typed movement/balance models and a separate public posting service over one controlled transaction engine. Posting uses row locks, deterministic unique keys, base-unit quantities, branch/warehouse validation, atomic ledger/balance updates, negative-stock prevention and immutable reversal movements.
- The manual Opening Stock workflow is implemented as a multi-line document across all three inventory domains. Drafts are editable, approval makes the document read-only, and posting creates idempotent `OPENING` ledger entries and balances. Quantity can use a base or mapped alternative unit; conversion is calculated server-side, cost is recorded per base unit, and opening is blocked after an item already has a movement in that warehouse.
- Stock Transfer is implemented as a mixed-domain `DRAFT → POSTED` document. Posting atomically creates `TRANSFER_OUT` in the source and `TRANSFER_IN` in the destination, supports same-branch and cross-branch warehouse/showroom movement, blocks insufficient stock, converts mapped units to base quantity and is retry-idempotent.
- Manual Stock Adjustment is implemented as a mixed-domain `DRAFT → APPROVED → POSTED` document. `GAIN` always posts IN; `LOSS`, `DAMAGE` and `WASTAGE` always post OUT; `CORRECTION` requires an explicit direction. Posting uses mapped-unit conversion, atomic ledger/balance updates, negative-stock protection and retry-idempotent keys.
- Stock Ledger is implemented as one read-only cross-domain movement view over Raw Material, Part and Finished Product ledgers. It supports inventory/item, branch/warehouse, movement, direction and date filters; shows IN/OUT, source reference, unit cost and true chronological running balance; and links retained source documents when permitted.
- Purchase Order is implemented as a mixed Raw Material/Part document with supplier and receiving warehouse, server-controlled purchase-unit conversion, exact quantity/rate totals and `DRAFT → APPROVED/CANCELLED` control. Its creation screen uses an equal 50/50 open purchase catalogue and order form/cart: compact four-column image cards, fixed catalogue filters, Raw Material/Part tabs and one-click item selection. Supplier mapping is optional metadata: mapped/preferred items are highlighted and ordered first, while unmapped active Raw Materials and `BUY`/`BOTH` Parts remain purchasable. Order discount supports `FLAT` and `PERCENT`, while preserving the calculated amount as a historical snapshot. `MAKE`-only parts remain blocked by business policy. A PO deliberately creates no stock movement, balance or journal; those effects begin only when a Purchase Receipt is posted.
- Purchase Receipt is implemented for both approved/partial Purchase Orders and direct receiving. Its 50/50 purchasing workspace keeps Direct Receipt open to all active purchasable items, while PO-based Receipt shows only pending order items with Ordered/Received/Pending context. Receipt Source and Supplier share one compact row, and an optional PDF/JPG/PNG supplier-invoice attachment is stored with the receipt. Drafts remain editable and have no stock effect. Posting is atomic and retry-idempotent: actual quantities/rates are converted and snapshotted server-side, Raw Material/Part stock is posted IN, linked PO received quantities are locked and updated, over-receipt is blocked, PO status becomes `PARTIAL` or `RECEIVED`, and a balanced finance journal is created as `DRAFT`. Gross Raw Material/Part inventory and Input Tax are debited; Purchase Discount and Supplier Payable are credited.
- Purchase Return is implemented only against a posted Purchase Receipt. Supplier, warehouse, source item/unit, conversion and original receipt rate are locked from the receipt; users enter return quantity, date and reason. Draft has no stock effect. Posting is atomic and idempotent, writes Raw Material/Part stock OUT in the receipt warehouse, prevents cumulative over-return and negative stock, keeps the return visible in Stock Ledger, and creates a `DRAFT` finance reversal: Supplier Payable debit against the corresponding Raw Material/Part Inventory credit.
- Finance Foundation is journal-safe: five typed account groups carry mandatory normal balances, starter accounts including Cash, Bank, Owner Capital and Partner Capital are idempotently branch-assigned, account codes/hierarchy and fiscal-year overlaps are controlled, mapped accounts cannot be disabled/removed, and displayed balances include only POSTED journals/opening balances. Purchase Account Mapping supports company defaults plus branch overrides for Raw Material Inventory, Part Inventory, Supplier Payable, Input Tax and Purchase Discount. The Balanced Draft Journal service enforces one active fiscal year, branch-assigned active BDT accounts, exact four-decimal debit/credit equality, debit-or-credit line rules, deterministic voucher sequences, `DRAFT`-only creation and unique posting/source idempotency. Purchase Receipt/Return posting now invokes this service inside the same database transaction as stock posting; finance configuration failure rolls back the entire operation. `finance:reconcile-purchase-journals` safely creates any missing drafts for older posted documents.
- Journal Entries is independently permissioned and branch-scoped. It supports list/detail review, status/source filters, approval of balanced Drafts and posting only after fresh fiscal-year/branch-account validation. Posting records the actor/time and is the only point at which balances are affected. A source-generated Draft cannot be voided separately from its already-posted business document; it must be posted and corrected through a linked reversal. Non-source Drafts retain audited void support.
- Account Ledger is independently permissioned and branch-scoped. It displays only POSTED journal lines and POSTED account opening balances, with account/branch/date filters, Dr/Cr debit-credit columns, source-journal navigation and a true chronological running balance per account/branch. A date filter hides older rows but preserves their balance brought forward.
- A reusable Sinetec Image Picker now progressively enhances a standard `<input type="file" class="js-image-picker">` with compact dashed upload, preview, filename/size, replace/remove, drag-and-drop and configurable single/multiple modes on both full pages and AJAX modals. Raw Material, Part, Finished Product, Payment Type, Brand, Supplier and Customer now use it; no active retained screen executes Spartan.
- Opening Stock CSV import is optional and deferred; add it later if go-live volume makes manual entry impractical.
- Supplier Payment supports receipt-specific partial payment, a selected branch-assigned Cash/Bank account and a Draft payment journal. `accounts.is_cash_bank_account` explicitly controls payment eligibility, so Inventory, Receivable and other non-liquid Asset accounts cannot be used as payment sources. Payment posting reduces operational supplier due; only accountant-posted journals affect the Account Ledger. Payment correction is audit-safe: Draft payment may be voided with a reason; Posted payment becomes `REVERSED`, restores supplier due and either voids its unposted journal or creates one linked journal reversal Draft. Journal list/detail now recognises Supplier Payment as a navigable source.
- Supplier Due Summary is independently permissioned and branch-scoped. It calculates each supplier's current position from Posted receipts minus Posted returns and Posted payments; Void/Reversed payments do not reduce due. Purchase Price History exposes original Posted receipt-line rates for Raw Materials and Parts.
- Finance Opening Balance is independently permissioned and branch-scoped. One balanced opening set is stored per active Fiscal Year + Branch using the existing `account_opening_balances` account rows. Only active, BDT, branch-assigned accounts are accepted; every line has exactly one Debit or Credit and totals must equal. A Draft can be replaced as one controlled set; posting atomically locks it, makes it immutable and exposes the rows in Account Ledger from the fiscal-year start date.
- Cash/Bank Book is independently permissioned and branch-scoped. It derives movement only from Posted opening balances and Posted journal lines for accounts marked `is_cash_bank_account`, with Money In, Money Out, source-journal navigation and true chronological running balance. It is read-only and never creates a second ledger table.
- Capital Investments is independently permissioned and branch-scoped. Owner or Partner funds received after go-live are recorded in `finance_capital_investments` as a Draft, using an assigned Cash/Bank Asset account and an assigned Equity account. Posting the document produces a reviewable Receipt Voucher Draft: Debit Cash/Bank and Credit Capital. Only the accountant-posted journal reaches Cash/Bank Book and Account Ledger; a Draft can be voided with audit reason.
- Loan Receipt, Capital Withdrawal, Cash/Bank Transfer and Loan Repayment are independently permissioned, branch-scoped controlled documents. They respectively create Draft journals for Cash/Bank received against Loan Liability; Drawings against Cash/Bank; destination Cash/Bank against source Cash/Bank; and Loan Liability against Cash/Bank. Cash/Bank Transfer is intentionally restricted to the same branch; cross-branch transfer needs a future inter-branch clearing design.
- Trial Balance is independently permissioned and branch-scoped. It derives only from Posted account-opening rows and Posted journal lines as of the selected date, displays debit/credit movement and closing Dr/Cr position, and clearly reports whether total debit equals total credit. It stores no duplicate reporting balance table.
- Fiscal Year Closing is independently permissioned and branch-scoped. One document closes a selected Owner/Partner Drawings debit balance into a selected Capital account at the active fiscal year end. It cannot be prepared before that end date; its amount is calculated only from Posted opening/journal rows, and it creates a balanced Draft Closing Journal (Debit Capital, Credit Drawings). Another fiscal year cannot be activated while the current year has a Draft journal, Draft closing, or prepared closing journal that remains unposted.
- The 7 November Finance audit fixed Trial Balance's local branch filter while the topbar is in All Branches mode, protected Loan Repayment detail/due access by branch, made Cash/Bank Transfer amount normalization exact at four decimals, added Cash/Bank Transfer as a navigable Journal source, and cleaned the worst minified Finance/controller/route code. Finance application files now pass Pint; route and Blade caches compile.
- The draft generator never posts a journal automatically. BOM/manufacturing follows the remaining purchase-finance work.
- Test retained Supplier/Customer CSV imports against the clean schema.
- Review public registration before production; unrestricted role selection must not be exposed.
